# OpenTime Prototype Plan v0.2

## 1. 文書の目的

本書は、OpenTime の試作開発に向けた初期計画書である。

OpenTime は、正確な時刻をネットワーク内の機器へ配信するための、オープンソースの時刻同期アプライアンスを開発するプロジェクトである。

本書の主な読者は、電子工作やネットワーク機器に詳しい技術者だけではなく、プロジェクトの価値、必要性、資金用途を判断する支援者、協力者、一般の意思決定者を想定する。そのため、専門用語は必要最小限にし、使う場合は文末の用語集で補足する。

本書で明確にする内容は以下である。

- OpenTime が何を作るプロジェクトなのか
- なぜ時刻同期が重要なのか
- 初期モデルとして何を作るのか
- なぜこの構成を選ぶのか
- いくらの支援を必要としているのか
- その資金で何を購入し、何を検証するのか

## 2. プロジェクト名と製品名

## 3. 背景と課題

### 3.1 なぜ時刻同期が重要なのか

コンピュータやネットワーク機器は、それぞれ内部に時計を持っている。しかし、その時計は完全ではなく、時間が経つにつれて少しずつずれる。

家庭用の時計が数日から数週間で数秒ずれるのと同じように、サーバー、ルーター、スイッチ、監視装置の時計もずれる。小さなずれに見えても、ネットワークやセキュリティの世界では大きな問題になる。

たとえば、以下のような場面で正確な時刻が必要になる。

- 障害が起きたとき、どの機器で最初に問題が起きたのかを調べる
- 不正アクセスがあったとき、攻撃者がどの順番で何をしたのかを追跡する
- 複数のサーバーにまたがるログを時系列で並べる
- 仮想化基盤やストレージのイベントを正しく比較する
- 監視システムで障害発生時刻を正しく記録する
- 認証、証明書、暗号化通信の期限判定を正しく行う
- 取引、決済、製造、医療、研究など、記録の正確性が重要な業務を支える

時刻がずれていると、ログの順序が入れ替わる。ログの順序が入れ替わると、障害調査やセキュリティ調査で「何が先に起きたのか」が分からなくなる。

これは、事故現場の監視カメラがそれぞれ別の時刻を表示している状態に近い。映像は残っていても、時計がずれていれば、出来事の順番を正確に再現できない。

### 3.2 身近な例

たとえば、会社のネットワークで以下のような障害が起きたとする。

1. インターネット接続が不安定になる
2. 社内システムへログインできなくなる
3. サーバーの一部が応答しなくなる
4. 監視システムがアラートを出す

このとき、各機器の時計が正確にそろっていれば、担当者はログを時系列に並べて原因を追える。

しかし、ファイアウォール、スイッチ、サーバー、監視システムの時計がそれぞれ数秒から数分ずれていると、原因と結果の順番が逆に見えることがある。その結果、復旧に時間がかかり、誤った対策をしてしまう可能性がある。

### 3.3 エンタープライズ機器で求められる時刻

Cisco、アライドテレシス、Juniper、Fortinet、Palo Alto Networks などのネットワーク機器は、ログ、認証、証明書、監視、障害解析のために NTP による時刻同期を利用する。

大規模なネットワークでは、機器の数が多く、ログの量も膨大になる。そのため、すべての機器が同じ時刻を基準に動いていることが重要である。

OpenTime は、こうしたエンタープライズ機器が求める「安定した時刻の供給」を、個人、ホームラボ、小規模事業者、教育機関、研究用途でも導入しやすい形で提供することを目指す。

### 3.4 既存の課題

高精度な専用タイムサーバーは存在するが、一般に高価である。また、小規模環境や個人の検証環境では導入しづらい。

一方、安価な小型コンピュータと GPS 受信機を組み合わせて時刻サーバーを作る方法もある。しかし、多くの場合、以下の課題が残る。

- 電源が抜けやすい
- 電源が 1 系統しかなく、電源障害に弱い
- ストレージ故障に弱い構成になりやすい
- 時刻源、電源、ネットワークの状態が分かりにくい
- ラックにきれいに収まらない
- 長期運用や保守を考えた設計になっていない
- 同じものを他人が再現しにくい

OpenTime は、安価な自作機ではなく、再現可能で、見える化され、常時運用を前提にした時刻同期アプライアンスを目指す。

## 4. プロジェクトの目的

OpenTime の目的は、エンタープライズ機器が必要とする安定した時刻同期を、より手の届きやすい形で提供することである。

OpenTimeServer では、以下の達成を目指す。

- Cisco やアライドテレシスなどのネットワーク機器が参照できる NTP サーバーとして動作すること
- ネットワーク内の複数機器へ安定した時刻を配信できること
- 障害調査、セキュリティ調査、監視運用で信頼できる時刻基準を提供すること
- 衛星測位システムから得た正確な時刻を利用すること
- 片側のコンピュータが停止しても、もう片側がサービスを継続できること
- 片側の電源が停止しても、システム全体が継続動作できること
- 時刻同期、電源、ネットワーク、温度などの状態を見える化すること
- 回路、基板、筐体、ソフトウェア、部品表、組み立て手順を公開し、再現可能にすること

## 5. 今回作りたいもの

今回作りたいものは、**OpenTimeServer の試作機** である。

OpenTimeServer は、ラックに設置できる小型の時刻サーバーであり、ネットワーク内のルーター、スイッチ、サーバー、仮想化基盤、監視システムに正確な時刻を配信する。

初期モデルでは、次の特徴を持たせる。

- 小型コンピュータを 2 台搭載する
- 片方を通常運用、もう片方を待機用として使う
- 電源を 2 系統搭載する
- 衛星から時刻を受信する
- ネットワーク機器に NTP で時刻を配信する
- 前面表示または監視機能で状態を確認できる
- 将来的に 19 インチラックへ搭載できる形を目指す

### 7.3 動作イメージ

通常時は CM5-A が時刻サーバーとして動作し、CM5-B は待機する。CM5-A が停止した場合、CM5-B が自動的に役割を引き継ぐ。

電源は A 系統と B 系統を持つ。片方の電源が抜けても、もう片方の電源で動作を続ける。

衛星から受け取った時刻情報は、2 台のコンピュータに同時に配る。これにより、待機側も常に正確な時刻を保持し、切り替え時にすぐ動作できる。

## 8. なぜ Raspberry Pi Compute Module 5 を選ぶのか

Raspberry Pi Compute Module 5 は、小型コンピュータである Raspberry Pi 5 の中核部分を、組み込み機器向けに小さなモジュールにした製品である。一般的な Raspberry Pi と違い、HDMI、USB、LAN などの端子が最初から付いている完成基板ではなく、専用の基板に組み込んで使う。

OpenTimeServer では、完成品の小型コンピュータをそのまま箱に入れるのではなく、電源、ネットワーク、表示、時刻信号の配線をまとめた専用基板を作る。そのため、Compute Module 形式の製品が適している。

CM5 を選ぶ理由は以下である。

### 8.1 専用機器として設計しやすい

通常の Raspberry Pi は試作には便利だが、製品のように筐体へ組み込む場合、端子の位置や電源の取り回しに制約が出やすい。

CM5 は専用基板に載せて使う前提のため、LAN ポート、電源端子、表示、アンテナ端子などを OpenTimeServer に適した位置へ配置できる。

### 8.2 microSD カードに依存しない

小型コンピュータでは microSD カードを保存装置として使うことが多い。しかし、常時稼働する機器では、microSD カードの劣化や突然の故障が問題になりやすい。

CM5 には eMMC という基板上の保存装置を搭載したモデルがある。OpenTimeServer では eMMC 搭載モデルを選び、microSD カードを使わない方針とする。

### 8.3 長期運用に向いた構成を作りやすい

OpenTimeServer は、電源を入れて終わりではなく、常時稼働させる機器である。そのため、安定した起動、設定の保存、ログの管理、将来のソフトウェア更新が重要になる。

CM5 の 4GB メモリ、32GB eMMC 構成は、時刻サーバーとしては余裕のある構成である。この余裕により、監視機能、表示機能、更新機能、診断機能を追加しやすくなる。

### 8.4 2 台構成にしやすい

OpenTimeServer は、1 台が止まってももう 1 台が引き継ぐ構成を目指す。CM5 は小型で、同じ基板上に 2 台搭載する設計がしやすい。

### 8.5 オープンソース開発と相性がよい

Raspberry Pi 系の製品は利用者が多く、Linux や周辺ツールの情報が豊富である。これにより、プロジェクトに参加する人が環境を再現しやすい。

OpenTime は OSS として公開するため、特殊すぎる部品だけで構成するより、広く知られた基盤を使う方が参加しやすい。

## 11. フェーズ計画

### Phase 0: 計画と購入準備

目的は、購入対象を明確にし、支援者や協力者へ説明できる状態にすることである。

成果物:

- 試作計画書
- 購入候補一覧
- 全体構成図
- 検証項目一覧

### Phase 1: 1 台構成で時刻サーバー化

目的は、CM5 1 台と GNSS 受信機を使い、ネットワーク内へ正確な時刻を配信できるか確認することである。

確認すること:

- 衛星から時刻を受信できるか
- CM5 が時刻信号を受け取れるか
- ネットワーク内の機器が OpenTimeServer を時刻サーバーとして参照できるか
- 時刻のずれが安定して小さく保てるか

### Phase 2: 2 台構成で切り替え検証

目的は、CM5 を 2 台使い、片方が停止してももう片方が時刻配信を引き継げるか確認することである。

確認すること:

- 通常側と待機側の切り替えができるか
- 切り替え時に時刻配信が止まりにくいか
- ネットワーク機器から見て同じ時刻サーバーとして扱えるか

### Phase 3: 電源 2 系統化の検証

目的は、片方の電源が抜けても動作を継続できるか確認することである。

確認すること:

- 電源 A のみで起動できるか
- 電源 B のみで起動できるか
- 動作中に片方の電源を抜いても止まらないか
- 電源異常を検出できるか

### Phase 4: 専用基板の設計準備

目的は、机上試作で得た結果をもとに、専用基板の設計に入ることである。

確認すること:

- 必要な端子の種類
- 電源回路の構成
- 信号の配線
- 表示部との接続
- 筐体に必要なサイズ

### Phase 5: 筐体設計

目的は、OpenTimeServer をラックに設置できる形へまとめることである。

確認すること:

- 1U と 2U のどちらが適切か
- 電源コネクタを抜けにくくできるか
- アンテナ端子をどこに置くか
- 前面表示をどう配置するか
- 熱を逃がせるか
- 保守しやすいか

## 12. 成功条件

| リスク | 内容 | 対策 |

| 時刻受信機の選定ミス | 測位向け製品を選ぶと時刻用途に最適でない可能性がある | タイミング向け GNSS を優先し、評価基板で確認する |
| 電源設計の難しさ | 2 系統電源は単純な配線では実現できない | 評価基板で段階的に検証する |
| 発熱 | CM5 を 2 台使うため筐体内温度が上がる | ヒートシンク、ファン、温度監視を検討する |
| 予算超過 | GNSS、基板、筐体は価格変動が大きい | 初期購入を机上試作に絞り、段階的に購入する |
| 専門性の高さ | 一般支援者に価値が伝わりにくい | 障害調査、セキュリティ、ログ管理の具体例で説明する |
